Based on the provided section of the 3GPP specification, the key procedural steps for the UE initiating the registration procedure for mobility and periodic registration update are:

1.  **Determine the Triggering Condition:** The UE first determines *why* it needs to initiate the registration procedure. This is based on the conditions listed a) through zp) and zm1), zn), and zq).

2.  **Send REGISTRATION REQUEST Message:** The UE sends a `REGISTRATION REQUEST` message to the AMF.

3.  **Set 5GS Registration Type IE:** The UE sets the `5GS registration type IE` based on the specific reason for the registration (mobility registration updating, periodic registration updating, disaster roaming mobility registration updating).

4.  **Handle S1 Mode Support (if applicable):** If the UE supports S1 mode, has not disabled its E-UTRA capability, and the registration is for specific reasons (e.g., emergency services fallback while supporting S1 mode), the UE sets the S1 mode bit to "S1 mode supported" in the 5GMM capability IE and includes the S1 UE network capability IE. The UE may also include the EPS-UPIP bit. HO attach bit should be set if supported.

5.  **Set Capability Bits in 5GMM capability IE:** The UE sets various capability bits in the `5GMM capability IE` of the `REGISTRATION REQUEST` message to indicate supported features such as LPP, LCS, RACS, 5G-SRVCC from NG-RAN to UTRAN, restriction on the use of enhanced coverage, network slice-specific authentication and authorization, CAG feature, extended CAG information list, enhanced CAG information, sending of REGISTRATION COMPLETE message for acknowledging the reception of Negotiated PEIPS assistance inforation IE, NSAG, the unavailability period, network slice replacement, ciphered broadcast assistance data, WUS assistance information, NR-PSSI, service gap control, multiple user-plane resources in NB-N1 mode, extended rejected NSSAI, NSSRG, 5G ProSe features, UAS services, the N1 NAS signalling connection release, the paging indication for voice services, the reject paging request, the paging restriction, MINT, slice-based N3IWF selection, slice-based TNGF selection, A2X over E-UTRA-PC5, A2X over NR-PC5, A2X over Uu, event notification, SSNPNSI, ESI, LADN-DS, Reconnection to the network due to RAN timing synchronization status change (RANtiming), MPSIU, MCSIU, ranging and sidelink positioning (RSLP), partial network slice, network slice usage control, S-NSSAI time validity information and S-NSSAI location validity information.

6.  **Include UE Policy Container (if applicable):** If the UE is operating in single-registration mode and performs inter-system change from S1 mode to N1 mode, it may include the `Payload container IE` set to "UE policy container" and include the `UE STATE INDICATION` message.

7.  **Handle SMS over NAS:** If the UE needs to request the use of SMS over NAS transport or the current requirements to use SMS over NAS transport change in the UE, the UE shall set the SMS requested bit of the 5GS update type IE in the REGISTRATION REQUEST message.

8.  **Start Timers:** After sending the `REGISTRATION REQUEST` message, the UE starts timer T3510 and stops timer T3502 and T3511 if those timers are running.

9.  **Include Last Visited Registered TAI (if available):** The UE includes the last visited registered TAI in the `REGISTRATION REQUEST` message if available.

10. **Handle 5GS Mobile Identity:** The UE includes the `5GS mobile identity IE` with either a valid 5G-GUTI or a 5G-GUTI mapped from a valid native 4G-GUTI if performing inter-system change from S1 mode to N1 mode, or the SUCI. The UE might also include the NID if the UE is registering with an SNPN and the valid 5G-GUTI was previously assigned by another SNPN. The UE may include the additional GUTI IE.

11. **MICO Mode (if applicable):** If the UE supports and requests MICO mode, it includes the `MICO indication IE`, `T3324 IE`, and optionally the `Requested T3512 value IE`.

12. **DRX Parameters (if applicable):** If the UE needs to use or change the UE specific DRX parameters, the UE shall include the Requested DRX parameters IE in the REGISTRATION REQUEST message for all cases except case b.

13. **eDRX Parameters (if applicable):** If the UE supports eDRX and requests the use of eDRX, the UE shall include the Requested extended DRX parameters IE in the REGISTRATION REQUEST message.

14. **LADN Information (if applicable):** If the UE needs to request LADN information, it includes the `LADN indication IE`.

15. **Uplink Data Status (if applicable):** The UE may include the `Uplink data status IE` to indicate PDU sessions with pending user data.

16. **PDU Session Status (if applicable):** When initiated in 5GMM-IDLE mode, the UE may include the `PDU session status IE`. If the UE received a paging message with the access type indicating non-3GPP access, the UE shall include the Allowed PDU session status IE in the REGISTRATION REQUEST message.

17. **UE Status (if applicable):** If the UE is operating in the single-registration mode performs inter-system change from S1 mode to N1 mode, the UE shall include the UE status IE with the EMM registration status set to "UE is in EMM-REGISTERED state" in the REGISTRATION REQUEST message.

18. **EPS NAS message container (if applicable):** If the UE is operating in the single-registration mode performs inter-system change from S1 mode to N1 mode and the registration procedure is initiated in 5GMM-IDLE mode, the UE shall/may include a TRACKING AREA UPDATE REQUEST message as specified in 3GPP TS 24.301 [15] in the EPS NAS message container IE in the REGISTRATION REQUEST message.

19. **Requested NSSAI (if applicable):** The UE includes the `Requested NSSAI IE` or the `Requested mapped NSSAI IE` containing the S-NSSAI(s) to which it intends to register, considering configured, allowed, and default NSSAI. The S-NSSAI(s) should be associated with at least one common NSSRG value if the NSSRG information is available.

20. **Unavailability Information (if applicable):** For case zm1, if the network indicated support for the unavailability period in the last registration procedure, the UE shall include the Unavailability information IE in the REGISTRATION REQUEST message.

21. **Follow-on Request Indicator:** The UE sets the `Follow-on request indicator` to "Follow-on request pending" if applicable.

22. **5GS Update Type IE (if applicable):** For case n, the UE shall include the 5GS update type IE in the REGISTRATION REQUEST message with the NG-RAN-RCU bit set to "UE radio capability update needed".

23. **Service-level-AA container IE (if applicable):** For case zf, the UE shall include the service-level device ID in the Service-level-AA container IE of the REGISTRATION REQUEST message and set the value to the CAA-level UAV ID.

24. **NAS message container (if applicable):** The UE shall send the REGISTRATION REQUEST message including the NAS message container IE as described in subclause 4.4.6.

25. **Unavailability information IE (if applicable):** For case zm1, if the network indicated support for the unavailability period in the last registration procedure, the UE shall include the Unavailability information IE in the REGISTRATION REQUEST message.

26. **UE request type IE (if applicable):** If the network supports the N1 NAS signalling connection release, and the MUSIM UE requests the network to release the NAS signalling connection, the UE shall set Request type to "NAS signalling connection release" in the UE request type IE, set the Follow-on request indicator to "No follow-on request pending" and, if the network supports the paging restriction, may set the paging restriction preference in the Paging restriction IE in the REGISTRATION REQUEST message.

These steps outline the UE's actions in initiating the mobility and periodic registration update procedure.
